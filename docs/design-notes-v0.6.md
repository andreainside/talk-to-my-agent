# v0.6 方案(待 the owner 过目后开工)

四件事,按依赖顺序排。前两件是桥的结构性改动,后两件是新能力。

---

## ① 工位迁移:员工在仓库里干活,记忆另放

**问题(已核实)**:员工 cwd 是它的家目录,不在 the repository里。Claude Code 以 cwd 为根加载项目指令与技能,结果 the repository的 **dozens of AGENTS.md、all仓库级 skill 全部不可见**——它今天所有的 the project 诊断都是在不懂 the project 任何规矩的状态下做的;只要让它改代码/开 PR,就会违反一半约定而不自知。

**方案**:
- cwd 改为 `workdir`(它的专用 worktree)。dozens of AGENTS.md 按目录级联生效,仓库 skill 全部可用(`production-inspector`、`pull-requests`、`codex-review`…)。
- 家目录改用 `--add-dir <home>` 挂载:它的 CLAUDE.md(记忆)照样自动加载,笔记照样写在家里,且永远在 git 之外。
- Codex 同理:`thread/start` 的 `cwd` 改为 workdir,家目录 AGENTS.md 作为 `developerInstructions` 注入。
- `~/.claude/projects/` 加入阅读区——员工替你查别的会话进度是它的本职(今天干了四次,每次请示一次)。

**已验证**:`--resume` 跨 cwd 有效(实测换目录后仍记得暗号)。**员工不会重新入职,对话历史不丢**。唯一变化:它们的会话归档目录从 `-Users-<user>--talk-to-my-agent-home-*` 变为 `-Users-<user>-the project-repo-<workdir>`。

**验收**:迁移后让the feedback group员工跑一句 `@bot 你现在能看到哪些 skill、读了哪几份 AGENTS.md`,对比迁移前(只有全局 skill、零份 AGENTS.md)。

## ② 版本与更新通知

**现状**:十几个版本、零 CHANGELOG、零 tag。团队装的是"克隆下来就再也不会动"的代码,没人会天天看 GitHub。

**方案**(全程零 token,无 agent 参与):
- **发版侧**:打语义化 tag(v0.6.0),`CHANGELOG.md` 顶部一段人话(版本、日期、三五条变化、`⚠ 需改配置` 标记),`gh release create` 用同一段做 release notes。
- **桥侧**:启动时 + 每天一次 `git fetch` 项目仓库(纯网络请求)。发现新 tag → 读 CHANGELOG 对应段 → bot **私聊 owner** 一条模板消息(只私聊、不进群、同一版本只通知一次):

  > 🔄 talk-to-my-agent 有新版本 v0.6.0:
  > • …(CHANGELOG 原文)
  > 回 `update` 我就拉取并重启;不回就维持现状。

- **更新**:owner 私聊 `update` → 桥 `git fetch && git checkout <tag>` → 检测配置缺字段(有则提示是否按默认值补)→ `reload`。owner 不碰终端。
- **不做**:自动拉取(在别人机器上跑我推的代码,必须 owner 点头);GitHub watch 邮件(链条太长,对团队等于没有)。

**验收**:打 v0.6.0 后,我自己的 bot 私聊收到通知;回 `update` 后 `status` 显示新版本号。

## ③ 一对一小群:人的地址,而不是话题的场合

**洞察(the owner)**:大家都在所有群里,"a teammate在 the team group 群"不是事实——群是话题的场合,不是人的地址。所以"中心 Agent 判断该发哪个群"这个路由问题是人造的,不该存在。

**方案**:每对人一个小群「A × B」,成员四个:A、B、A 的 bot、B 的 bot。
- **地址唯一**:要找a teammate = 去「the owner × a teammate」群发。不需要任何路由判断。
- **场合正确**:一对一的事不打扰全班;公共的事仍去大群。
- **对称**:a teammate的开发会话要找你,走同一条线反过来。
- **bot 互 @ 天然落地**:两人的 agent 在同一间屋里,昨天做的 thread 归属、转交机制全部适用。
- 桥对小群**零特殊处理**:它就是一个普通群,有自己的员工、自己的记忆。

**建群**:bot 能建群(昨天建实验群就是这么建的)。an N-person team = N(N-1)/2 groups,一次建完噪音太大;建议**用到再建**——第一次要找某人时建,建完写进通讯录。建群本身是对外动作,走审批。

**通讯录**:`shared/TEAM.md` 的 People 段——**不预填,由 agent 自己问出来**。它第一次需要找人时不知道找谁,就问 owner("这个权限的事该找谁?");owner 说"找a teammate",它去找,成功后记一行"网关配置权限 → a teammate(群 xxx)"。前几次全靠问,之后它能自己判断;判断不了的仍然问。TEAM.md 从第一天起就全是真实案例,而且它练的是"不知道就问"而不是"不知道就猜"。

**这意味着 agent 要有「主动开口问 owner」的能力**——它现在只会被动应答。这一点和之前定的"主动开口"方向重合:第一版只允许它**私聊 owner**问问题,不进群。

## ④ 开发会话的求助通道

**需求**:本机跑着的开发会话撞墙(缺权限 / 与人耦合 / 需决策 / 需信息)时,**不猜**,知道找谁、能以你的 bot 身份发出去、能收到回音。

**已否决**:
- 邮箱/求助单协议——为不存在的问题造消息队列,飞书本身就是那个队列。
- 中心 Agent 新角色——它本来不需要存在;所谓"翻译中介"只是在没有通讯录时的补偿。

**方案(没有新机制,三样东西)**:
1. **通讯录** = ③ 的 TEAM.md。开发会话能读(`allowed_read_roots` 已含员工家目录)。
2. **发消息** = `lark-cli`,开发会话本来就会。以你的 bot 身份发到对应小群,在那条 thread 里等回音(读 thread 免批)。
3. **求助意识** = 一段全局指令(`~/.claude/CLAUDE.md`)+ 一个 skill(`ask-the-team`):撞到四类墙,查通讯录,发出去,继续干能干的部分。指令给判断依据,不给死规则。

**审批边界**:发到一对一小群**免批**(影响面小);发到公共群**请示**(替你公开发言,你先看一眼)。这是 approval_hook 里一条按 chat_id 分档的规则。

**桥员工回归本位**:它们是各群的常驻同事,接群里的 @。开发会话不经过它们,它们也不当中介。开发会话以 bot 身份开的 thread,后续 @ 照样按"开口者归属"路由——开发会话也走 lark-cli,归属表顺手覆盖。

**依赖**:③ 先有至少一个小群和一份种子通讯录,④ 才有东西可用。

## 仓库边界:公开项目 vs 团队用法

项目是公开的、脱敏的。它提供的是**机制和引导**;每个团队的具体用法(谁管什么、有哪些群、约定)是**那个团队的 agent 在本机长出来的数据**,永远不进仓库。

| 进仓库(公开、通用) | 不进仓库(本机、团队私有) |
|---|---|
| 桥、hook、codex 后端 | `~/.talk-to-my-agent/` 整个目录 |
| `home_template/`(员工手册、TEAM.md 空模板) | 每个员工的家、笔记、TEAM.md 的内容 |
| `ask-the-team` skill 的机制部分(怎么查通讯录、怎么发、怎么等回音) | 通讯录内容、小群 chat_id |
| `docs/`(装法、配置、本方案的脱敏版) | 团队部署 MD(已有,含 worktree 建法、群规) |
| CHANGELOG、tag | — |

**"丝滑引导别的团队个性化"**靠两样:①员工手册和 TEAM.md 模板是**空的但有结构**——告诉 agent 该往哪记什么,不告诉它记什么;②`docs/agent-setup.md` 让装的人的 agent 采访装的人,把团队信息问出来写进本机配置,而不是让人填表。

**"让我们团队以我们的方式用"**靠那份不进仓库的团队部署 MD,已经有了;③④ 落地后补一段"我们怎么用一对一小群、agent 问你的时候怎么答"。

**脱敏纪律**:推之前 grep 一遍团队名、群 ID、人名(上次推前做过,这次照做)。本方案文档进仓库前也脱敏——群名、人名、"the project" 字样全替换。
